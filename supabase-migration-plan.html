Why GAS + GSheets is slow

Bottleneck What's happening Impact
Cold start Every GAS request spins up a new runtime (~1–3 sec before your code even runs) 2–3 sec delay
Row scanning getValues() loads the ENTIRE sheet then loops in JS — no indexes Slower as data grows
JSONP workaround No real API — forced to inject <script> tags; large payloads break Fragile, size-limited
GAS quotas 6 min max execution, 20k URL fetches/day, 50MB response limit Ceiling risk
Concurrent users GAS has no connection pooling — parallel requests queue up Degrades under load

What the code looks like after migration

Before (GAS + JSONP) — slow, fragile

// Fetch all batches — 2-4 seconds, breaks on large data
gasGet({action: 'getBatches', centre: 'Chennai'}, function(err, data) {
  // GAS scans every row of the Batches sheet
  renderBatches(data.batches);
});

After (Supabase JS client) — fast, typed, clean

// Same data in <50ms — indexed PostgreSQL query
const { data, error } = await supabase
  .from('batches')
  .select('*, students(count)')
  .eq('centre', 'Chennai')
  .eq('status', 'Active')
  .order('start_date', { ascending: false });

renderBatches(data);

Row-level security (replaces GAS counselor auth check)

-- Counselors can only see batches in their allowed centres
CREATE POLICY "centre_isolation" ON batches
  FOR SELECT USING (
    centre = ANY((
      SELECT centre FROM users
      WHERE id = auth.uid()
    ))
  );

Migration Roadmap — 3 Phases

Week 1 — Foundation
Set up Supabase + migrate core tables
Create Supabase project · Design schema (users, batches, students, sessions, fees) · Export GSheets → CSV → import to Supabase · Set up Row Level Security policies · Create Supabase API wrapper (replaces gas.js) · Keep GAS running in parallel
Week 2 — Switch counselor + instructor portals
Replace GAS calls with Supabase in UI
Replace gasGet() / _gasPost() with supabase.from() calls in counselor.html · Replace JSONP with direct fetch · Migrate login to Supabase Auth · Test batch management, fee recording, student enrolment · Deploy to Vercel — both old and new live simultaneously
Week 3 — Migrate remaining modules + cut over
Assessments, inventory, diplomas, online tests
Migrate inventory, assessments, revenue targets, diplomas · Migrate online test engine (biggest module) · Final data sync from GSheets → Supabase · Switch DNS / routing to Supabase-backed version · Keep GSheets as read-only archive for 30 days

Risks & mitigations

Risk Severity Mitigation
Data loss during migration High Keep GSheets as live backup until Supabase is verified; do a dry-run import first
Diploma PDFs still need Drive Medium Keep Google Drive for file storage; just move the metadata to Supabase. Or switch to Supabase Storage.
Online test module is complex Medium Migrate last, after simpler modules are proven. Keep GAS for tests until Week 3.
Supabase free tier limits Low Free tier supports 500MB DB and 2GB bandwidth — more than enough. Pro is $25/month if needed.
Email sending (welcome emails) Low GAS currently sends emails. Replace with Resend.com (free tier: 3k/month) or Supabase built-in email.

Recommendation

Start with Phase 1 only — create the Supabase project, set up the schema, and import the data. This is zero-risk (GAS keeps running) and lets you validate the data structure before writing any new UI code. Once the data is in Supabase and queries are fast, the motivation to complete Phase 2 becomes obvious. The total rewrite of gas.js logic into Supabase queries is mechanical work — each GAS action maps 1:1 to a Supabase query. The hardest part is the online test engine; everything else is straightforward CRUD.
